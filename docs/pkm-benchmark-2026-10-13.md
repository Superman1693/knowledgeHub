## 一、主流 PKM 现在是什么样子

### 1.1 两条根本分水岭

不是「功能多少」的区别，而是两个立场选择：

| 分水岭 | 一端 | 另一端 |
|---|---|---|
| **数据在哪** | 本地纯文本优先（Obsidian、Logseq、思源、Anytype） | 云端数据库（Notion、Tana、Roam、Mem） |
| **谁来维护** | 你自己链接、打标签、归档 | 系统自动捕获与连接（Tana、Mem） |

你的项目明确站在**本地优先 + 自己维护**这一侧，和 Obsidian / Logseq / 思源是同一象限。
下面的对比也只在这个象限内有意义——拿它和 Notion 比协作、和 Tana 比自动化，是错的赛道。

### 1.2 三类形态

| 形态 | 代表 | 核心隐喻 | 交换代价 |
|---|---|---|---|
| **文件库** | Obsidian、Logseq、思源 | 一堆互相链接的文档 | 强大但需要自己搭系统 |
| **数据库** | Tana、Capacities、Anytype | 带属性的对象与查询 | 表达力强，建模成本高 |
| **白板** | Heptabase | 卡片在空间里排列 | 适合研究综合，不适合全量内容 |

### 1.3 2026 年的共识能力（已是及格线）

调研中反复出现、可以视为「现在不做就不合格」的：

1. **双向链接 + 块级引用** — 你有 ✅
2. **知识图谱** — 你有 ✅
3. **本地纯文本存储**（数据主权） — 你有 ✅
4. **间隔复习 / 闪卡** — 你有 ✅（且比多数工具更完整：SM-2 + 遗忘曲线 + Anki 导出）
5. **PDF 批注** — **你没有** ❌（Logseq / 思源 / Obsidian 都有）
6. **网页剪藏 / URL 导入** — **你没有** ❌（所有主流工具都有，Obsidian 甚至官方出了 Web Clipper）
7. **移动端触达** — **你没有** ❌（只监听 127.0.0.1）
8. **AI 问答（RAG）+ 引用溯源** — 你有 ✅（**这一项你强于绝大多数**）
9. **相关笔记推荐** — 有后端，但没在阅读动线露出 ⚠️
10. **导出 / 数据可携带** — 你有 ✅（zip + front-matter）

### 1.4 两个最值得注意的竞品

**思源笔记**（同为中文、本地优先，定位最接近你）：
闪念速记（长按图标即记）、微信/浏览器/文件管理器快速收集、**局域网伺服（手机当随身服务器，电脑浏览器直接访问）**、WebDAV/S3 端到端加密同步、PDF 批注、数据库看板、动态大纲。

**Knota**（本地优先 AI 知识库，功能清单最像你）：
网页 URL 自动转 Markdown、**潜在连接（语义发现未链接笔记 + 附关联原因）**、**Wiki 巡检（孤立页面 / 重复资料 / 桥接页面）**、静态站导出、NL2SQL、从笔记生成 PPT/Word。

## 二、你的项目现状定位

### 2.1 强项（明确强于主流工具的地方）

这些是你**已经做到、而多数竞品做不到或做得更浅**的：

| 能力 | 你的实现 | 对比 |
|---|---|---|
| **混合检索调优** | 关键词 α=0.3 + 语义 β=0.7 + 可选 LLM 重排 | Obsidian 原生只有关键词；要靠社区插件 |
| **拼音检索** | 全拼 + 首字母，且用「音节合法性」排除英文误判 | 主流中文 PKM 都**没有**拼音搜索 |
| **拼错容错** | pg_trgm 编辑距离，且**仅在精确结果不足时启用** | 少有工具做，且有防污染设计 |
| **标题参与检索** | 标题命中 2 倍权重 | 多数工具标题与正文混在一起 |
| **隐私过滤在 SQL 层** | `ai_only` 在检索阶段排除，非提示词约束 | 云端工具的 AI 必然上传，本地工具少有细粒度开关 |
| **来源溯源到片段** | 引用可跳转到原文片段并高亮 | 部分工具只到文档级 |
| **复习闭环完整度** | SM-2 + 掌握度分布 + **遗忘曲线（真实数据算出）** + Anki 导出 | Logseq 有闪卡但无遗忘曲线；Anki 导出少见 |
| **冲突检测** | 409 + 并排对比，**不静默丢内容** | 本地文件类工具普遍存在静默覆盖问题 |
| **版本历史** | 逐行对比 + 回滚（回滚前自动备份） | 比多数工具完整 |

**结论：你在「检索 / 关联 / 复习」这三个闭环上做得比大多数主流工具更深。** 这不是客套——拼音检索、拼错容错、遗忘曲线这三项，上面调研的十几个产品里没有一个原生具备。

### 2.2 真实缺陷与不足

下面按「投入产出比」排序。**区分两类**：`缺能力`（要从头做）vs `有能力但没露出`（改动小、收益大）。

---

#### 🔴 P0｜输入漏斗缺失（最严重的结构性缺口）

> 调研中最一致的一条结论：**「捕获是瓶颈，不是检索」**。
> 原文：*"大多数知识条目在移动端到达（网页剪藏、截图、语音笔记、转发邮件）。在调优 LLM 之前，先设计移动分享 → vault 路径。"*
> 另一篇：*"The capture problem is the real bottleneck, and it's a mobile problem."*

你把「检索 / 关联 / 复习」做到了 90 分，但**「怎么把东西弄进来」只有 40 分**。目前只有两个入口：上传文件、应用内手写。知识库的价值取决于**流入量 × 复用率**，入口窄会直接掐住整个系统。

| # | 缺口 | 类型 | 说明 | 建议 |
|---|---|---|---|---|
| P0-1 | **网页剪藏 / URL 导入** | 缺能力 | 主流工具的标配入口。你完全没有：看到好文章只能复制粘贴，格式乱、元数据全丢、且**脱离了知识库**（不能双链、不能检索）。 | **做**。后端加 `POST /api/documents/from-url`：抓正文 → 转 Markdown → 存入收集箱。比浏览器扩展便宜得多，且覆盖 80% 场景（用户复制 URL 粘贴进来即可）。 |
| P0-2 | **移动端 / 局域网访问** | 缺能力 | 只绑 `127.0.0.1`，手机完全够不着。思源有「局域网伺服」、Logseq 有 Docker 部署方案——这是本地优先工具的通行做法。 | **做**。把 `backend_host` 改为可配置的 `0.0.0.0`，前端同源访问即可用手机浏览器；**必须同时加访问口令**（局域网≠可信网络）。这是小改动、大收益。 |
| P0-3 | **速记入口（低摩擦捕获）** | 缺能力 | 有「收集箱」但是被动的（未分类文档的暂存区）。`Ctrl+K` 只能跳转，**不能直接记一句话**。思源的「闪念速记」是这个场景的标准解法。 | **做**。`Ctrl+K` 面板加「记一笔」：输入文字 → 直接落进今日笔记或收集箱，不打断当前操作。几十行代码。 |

#### 🟠 P1｜能力已存在，但没在阅读动线上露出来（改动小、收益大）

| # | 缺口 | 类型 | 说明 | 建议 |
|---|---|---|---|---|
| P1-1 | **相关笔记不在阅读页** | 有能力没露出 | `GET /api/insights/related/{id}` **已实现**，但入口在「扩展模块 → 知识加工 → 跨文档关联」，需要**手动下拉选文档**。而「读到一半发现有篇相关笔记」正是它该出现的地方。调研把「AI Suggested Links」称为*2026 年知识管理的重头戏*。 | **做**。文档详情页右侧加「相关笔记」面板，直接调已有接口。**纯前端改动**，零后端工作量。顺带显示「关联原因」（已有相似度），并支持一键插入 `[[双链]]`。 |
| P1-2 | **无知识库体检** | 缺能力（半） | 重复检测**已有**（`/insights/duplicates`），但缺**孤立笔记**（零入链零出链，等于存了没用）和**待补充主题**的巡检。Knota 的「Wiki 巡检」正是这个。 | **做**。加 `GET /api/insights/health`：孤立笔记数 + 重复对 + 未分类堆积 + 长期未复习的高价值笔记。工作台出一张「知识库体检」卡片。 |
| P1-3 | **标签/关联靠手动** | 部分已有 | 标签 AI 推荐**已有**，`related` 能算语义相似，但**不生成链接建议**。 | 归入 P1-1，不必单列。 |

#### 🟡 P2｜输出与复用（决定长期价值）

| # | 缺口 | 类型 | 说明 | 建议 |
|---|---|---|---|---|
| P2-1 | **PDF 批注 / 高亮回链** | 缺能力 | 目前 PDF 只解析为文本整篇入库，**不能在原文上划线并把高亮带进笔记**。Logseq 的 PDF 批注被公认为其最强功能之一；思源也有。这是「读文献」场景的刚需。 | **缓**。工作量最大的一项（要 PDF.js 渲染层 + 坐标存储 + 高亮与 chunk 的映射）。且与「分块检索」的架构有冲突需要设计。建议放到 P0/P1 之后。 |
| P2-2 | **主题聚合页 / Wiki** | 缺能力 | 笔记是扁平的，没有「把散落笔记编译成一个主题页」的能力。Knota 的 Wiki 模块做这个。 | **缓**。可以用「已保存的检索条件」+ 摘要拼装出一个轻量版，成本远低于完整 Wiki。 |
| P2-3 | **静态站导出 / 分享** | 缺能力 | 只能导出 zip 给别人。 | **可做**。导出为可离线打开的 HTML 站点，工作量中等。 |
| P2-4 | **从笔记生成产出物** | 缺能力 | 已有「批量摘要」「思维导图」，但没有把知识变成**交付物**（PPT / Word 报告）。这是「输出倒逼输入」的最后一环。 | **看需求**。你环境里已有 `tencent-pptx` / `tencent-docx` 能力，接起来不算难。但先问自己是否真有产出需求。 |
| P2-5 | **结构化查询 / NL2SQL** | 缺能力 | 有「保存的检索条件」，但没有表格化多条件查询。 | **不做**。个人知识库的数据量级（几百到几千篇）用不上，属于过度设计。 |

#### ⚪ P3｜刻意不建议做的

| 项 | 理由 |
|---|---|
| **块级编辑器**（现在编辑器是 textarea + 预览） | 主流工具确实多为块编辑器，但改造是**伤筋动骨**的：块级引用、锚点、版本 diff、冲突检测全部要重做。而你**已经支持块级引用语法**（`[[标题#小节]]`），以 textarea 实现了核心价值。投入产出比极差。 |
| **协作 / 多人** | 与「本地个人知识库」的定位根本冲突。 |
| **任务管理 / Todo** | 每加一个领域就分散一份注意力。你有「错题本」「复习队列」已经是任务化了，够用。 |
| **邮件导入（EML/MBOX）** | 除非你确实用邮件当知识来源。调研里出现是因为企业场景。 |
| **端到端加密同步 / 多端同步** | 这是个大工程（冲突解决、加密、密钥管理）。当前用「局域网访问 + 手动备份」已能覆盖个人场景。 |

## 四、一条必须说清的话

调研里最扎心的一句：

> **「知识库的价值取决于复用，不取决于笔记数量。」**
> 判断工具是否有效的务实标准：*一个月后，能否在可接受的时间内找回一条关键资料，理解它当时为什么重要，并把它放进新的工作成果中。*

按这个标准，你的项目**在「找回」和「理解为什么重要」上已经做得比多数主流工具好**（混合检索 + 拼音 + 容错 + 溯源 + 复习闭环）。真正拖后腿的是两头：

- **入口太窄**（P0）——东西进不来，再好的检索也无米下锅
- **出口太少**（P2）——找回来了却用不出去

所以建议顺序不是「补更多检索功能」，而是**先把漏斗两端修好**。中间那段是你的护城河，不需要再加固了。
