# PDF 批注：技术方案与落地建议

> 编写日期：2026-10-14
> 适用项目：KnowledgeHub（本地个人知识库）
> 本文可直接作为实施依据，含数据模型、API、分阶段步骤与风险清单。

---

## 一、推荐结论

**在 PDF 上做「引文锚定」的高亮与批注**：用户在原文上划线，划中的**引文 + 页号 + 归一化矩形**三者一起存；
批注文字（用户自己的话）导出成一篇可检索、可双链、可出闪卡的 Markdown 笔记。

一句话概括这个方案的世界观：**不把高亮绑定到「页面坐标」，而是绑定到「这句话本身」**。

---

## 二、为什么推荐它（而不是别的）

### 2.1 前面的调研已经指向这里

`docs/pkm-benchmark-2026-10-13.md` 的结论是「检索/关联/复习已是护城河，缺的是漏斗两端」。
输入端的四块（文件导入、网页剪藏、速记、局域网）**已经补完**，输出端补了静态站与 Anki 导出。

现在剩下的最有价值的一块，是**「读」这个动作本身**——而它恰恰落在输入与理解的交界：

| 候选 | 为什么不是它 |
|---|---|
| 测试隔离（独立测试库） | 是**工程债**不是能力缺口。重要，但对「知识库好不好用」零影响；且它是纯重构，不会产生任何用户可感知的价值。适合在功能告一段落后单独做一轮。 |
| 从笔记生成 PPT/Word | 属输出端，但**依赖你真有产出需求**。调研时的判断是「先问自己是否真需要」——在没确认需求前投入不划算。 |
| 更多检索能力 | **不该做了**。检索已是护城河，再加是边际收益递减。 |
| 块级编辑器 | 改造伤筋动骨（块引用、锚点、版本 diff、冲突检测全要重做），且现有 textarea 已支持 `[[标题#小节]]`。 |
| **PDF 批注** | ✅ **推荐**。它是「读文献」这个高频场景的刚需，Logseq 靠它拿下学生与研究者群体；同时它能**天然接进已有的三个闭环**（见 2.2）。 |

### 2.2 它能把已有能力串起来——这是关键

新功能最怕「孤岛」。PDF 批注的特别之处在于，它几乎不需要新造轮子，而是把现有的三条链路接到新场景：

```
                     ┌──────────────────────────────┐
   读 PDF ──划线──►  │ 引文 + 页号 + 矩形 三重锚定    │
                     └──────────────┬───────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      【写入闭环】            【关联闭环】            【复习闭环】
   批注导成 .md 笔记      引文里有 [[双链]]       划线处一键出闪卡
   参与混合检索           → 反向链接 → 图谱        → SM-2 排期
   （零新检索代码）        （零新代码）            （复用 assist + srs）
```

- **写入闭环**：批注导出成 `data/documents/<uuid>.md`——与现有笔记完全同构，于是**混合检索、拼音检索、拼错容错、标题检索全部自动生效**，一行检索代码都不用改。
- **关联闭环**：批注正文里可以写 `[[双链]]`，于是反向链接、知识图谱、相关笔记自动接上。
- **复习闭环**：划线选中 → 复用已有的 `assist_service` 生成闪卡 → 进入 SM-2 队列。

**这是它比「做再多检索功能」更值钱的原因：一个功能激活三条已有链路。**

## 三、核心难点与解法

### 3.1 难点：坐标 ↛ 分块

你的架构里，PDF 已经被拆成 chunk，而 chunk 是**文本**、有 `page_no`，但**没有坐标**。
直觉上的做法是「每次高亮都算出它落在哪个 chunk 里」，然后用 chunk 做锚点。

**这个方向是错的**，三个原因：

1. **chunk 会被重切**。调整分块参数、或者升级分块算法（你已经做过语义分块 + 规则分块回退），
   边界就变了，所有历史批注的锚点集体失效。
2. **chunk 边界与实际句子不对齐**。用户划的是「一句话」，而 chunk 可能是「三句半」。
3. **同一段文字可能落在两个 chunk 里**（有 overlap，你是刻意保留的），锚点会摇摆。

### 3.2 解法：三重锚定，各管一件事

| 锚 | 存什么 | 管什么 | 失效条件 |
|---|---|---|---|
| **页号** | `page_no`（整数，**已有**） | 快速定位到第几页 | PDF 换版本后页码可能整体偏移 |
| **引文** | `quote`（划中的原文，规范化后） | **真正的身份**。定位不到坐标时，仍能全文搜到 | 只有原文本身被改写才失效（PDF 一般不会） |
| **归一化矩形** | `rects: [{x,y,w,h}]`，**除以页宽高**得到 0..1 | 重绘高亮的**像素位置** | 缩放/DPI 变化都不影响（已归一化）；PDF 换版可能错位 |

**引文是主锚，坐标是辅助。** 这个顺序很重要：

- 加载批注时，先按页取候选，再用 `quote` 在前端文本层里**重新匹配**坐标 —— 于是即便 PDF 被替换成同内容的新版本，高亮位置自动修正；
- 匹配失败的批注**不隐藏、不丢弃**，而是显示在侧栏并标「定位可能已失效」，同时保留 `quote` 供检索。**静默丢失用户的高亮是不可接受的**。

再补两个字段提升消歧能力（业界标准做法，Hypothesis 用的就是这套）：
`prefix` / `suffix`（引文前后各 ~32 字符）。当同一页里「因此我们可以认为」出现多次时，用它确定是哪一处。

### 3.3 坐标系：这类 bug 的高发区

必须一次性定清楚，否则会反复出「高亮整体偏移 20px」这种问题：

| 问题 | 结论 |
|---|---|
| **原点在哪** | 归一化到**页面可视区域（CropBox）的左上角**，x 向右、y 向下。与 Canvas 一致，前端不用做 Y 轴翻转。 |
| **用 MediaBox 还是 CropBox** | **CropBox**。MediaBox 含出血区，很多 PDF 两者不同，用错会整体偏移。 |
| **页面旋转** | 存 `rotation`（0/90/180/270）。旋转页的坐标要按 PDF.js `viewport` 换算，这是最容易漏的一条。 |
| **多栏 / 跨栏选择** | 一段选择可能产生**多个矩形**（跨行、跨栏），所以 `rects` 是**数组**而不是单个矩形。 |
| **归一化的分母** | 用 `viewport.width/height`（已含 scale），再除以 scale 得到与缩放无关的值。 |

**存储格式**
```json
{
  "page_no": 12,
  "quote": "因此我们可以认为，响应式的本质是依赖收集与触发",
  "prefix": "……上一句结尾",
  "suffix": "……下一句开头",
  "rects": [
    {"x": 0.121, "y": 0.334, "w": 0.712, "h": 0.019},
    {"x": 0.121, "y": 0.356, "w": 0.408, "h": 0.019}
  ],
  "rotation": 0
}
```

## 四、技术选型

| 层 | 选型 | 理由 | 备选与为何不选 |
|---|---|---|---|
| **PDF 渲染** | `pdfjs-dist`（前端） | 唯一能提供**可选中文本层**的方案。批注的本质是「划词」，图片做不到。Mozilla 维护、可自托管、离线可用，符合本地优先定位 | ❌ 后端 PyMuPDF 渲染页图：无法划词，只能画框，UX 差一个量级<br>❌ PDF.js 走 CDN：破坏离线承诺 |
| **Worker 打包** | `?url` 导入 + `GlobalWorkerOptions.workerSrc` | Vite 下 PDF.js worker 的经典坑。用 `?url` 让 Vite 处理指纹与路径，**不要**硬编码 CDN 路径 | ❌ 忽略 worker：PDF.js 会退回主线程解析，大文件直接卡死界面 |
| **文本层** | PDF.js 内置 `TextLayer` | 直接拿到文本节点与其变换矩阵，配合 `Range.getClientRects()` 换算矩形 | ❌ 自己从 content stream 抽文本：等于重写一遍 PDF.js |
| **坐标换算** | `pdfjsLib.Util.transform` | 官方工具函数，处理旋转与缩放 | ❌ 手写矩阵乘：旋转页必错 |
| **PDF 流式传输** | 复用 `FileResponse`（**已支持 Range**，Starlette 1.7.0 实测） | 大文件按需加载，不用整份下发 | ❌ 全量 base64 塞进 JSON：内存爆炸 |
| **批注存储** | 新表 `pdf_annotations`（Postgres JSONB 存 rects） | rects 是天然的多值结构，JSONB 比拆列或建子表都合适；且**不参与索引**，不需要独立列 | ❌ 建 `annotation_rects` 子表：为一组只读的几何数据建关系表是过度设计 |
| **批注检索** | **导出成 Markdown 笔记**，复用现有检索 | `data/documents/*.md` 是知识本体，导出的批注笔记与普通笔记同构 → 混合检索/拼音/容错/双链**全部自动可用** | ❌ 把批注 comment 伪装成 chunk 插进向量库：会污染 PDF 自身的片段列表，还要处理「批注改了如何增量重建索引」的同步问题，收益远不抵复杂度 |
| **闪卡生成** | 复用 `assist_service` | 已有「选中文字 → 生成卡片」的完整实现 | — |

## 五、数据模型

### 5.1 新表 `pdf_annotations`

```python
class PdfAnnotation(Base, IdMixin):
    __tablename__ = "pdf_annotations"

    document_id: FK -> documents.id  (ondelete CASCADE, index=True)
    page_no: int                      # 1-based，与 chunk.page_no 口径一致
    quote: str            (Text)      # 划中的原文（主锚）
    prefix: str | None    (Text)      # 引文前 ~32 字符，消歧用
    suffix: str | None    (Text)      # 引文后 ~32 字符
    rects: list[dict]     (JSONB)     # 归一化矩形数组
    rotation: int         (default 0)
    color: str            (default 'yellow')
    comment: str | None   (Text)      # 用户自己的批注文字
    created_at / updated_at
```

**索引**：
- `document_id`（按文档取批注是唯一高频查询）
- `(document_id, page_no)` 复合索引（按页渲染时取该页批注）

**外键 CASCADE**：删除 PDF 文档时批注自动清掉，避免孤儿数据。
⚠️ **但要同步登记进 `backup_service.DUMP_TABLES` 与 `CLEAR_ORDER`**——
项目约定第 1 条明确写了，历史上因为这个漏过三次表（glossary_terms / quiz_records / note_revisions）。
`CLEAR_ORDER` 里它必须排在 `documents` **之前**（先子后父）。

### 5.2 不改动的地方（重要）

- **不动 `chunks` 表**。批注不生成 chunk，不碰向量库。
- **不动检索层**。批注通过导出笔记参与检索，`retriever.py` 一行不改。
- **不加 `documents` 字段**。「这个文档有没有批注」用 COUNT 子查询即可；
  真需要缓存再加，不要提前加列。

## 六、API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/documents/{id}/file` | 流式提供原始 PDF（**已存在**，`download_original`，需确认支持 inline 而不只是 attachment） |
| `GET` | `/api/documents/{id}/annotations` | 列出批注；支持 `?page=N` 过滤 |
| `POST` | `/api/documents/{id}/annotations` | 新建（入参含页号、引文、矩形、颜色） |
| `PUT` | `/api/annotations/{aid}` | 改颜色 / 批注文字 |
| `DELETE` | `/api/annotations/{aid}` | 删除 |
| `POST` | `/api/documents/{id}/annotations/export` | 把批注导出为 Markdown 笔记，返回新文档 ID |
| `POST` | `/api/annotations/{aid}/cards` | 由引文生成闪卡（复用 `assist_service`） |

⚠️ **路由顺序**：`/annotations/export` 这类**静态段必须声明在 `/{document_id}` 之前**——
项目约定第 5 条，历史上踩过（`/link-targets` 被当 UUID 解析返回 422）。

## 七、分阶段实施步骤

**原则：先验证最不确定的部分，再投入做功能。** 坐标系是整个方案唯一可能「做了才发现不对」的地方，所以放在阶段 0。

### 阶段 0：技术验证（建议先只做这一步，确认后再继续）

目标：**证明「划词 → 存 → 重绘」在坐标系上是对的**，其他都先不管。

1. 装 `pdfjs-dist`，在 Vite 里配好 worker（`?url` 导入）
2. 做一个最简页面：渲染 PDF + 文本层
3. 划词 → `Range.getClientRects()` → 换算成归一化矩形 → `console.log`
4. 用记录下的矩形，在**改变缩放后**重新画一层半透明 `<div>`，看是否严丝合缝对齐

**验收标准**：缩放 50% / 100% / 200% 三档下，高亮都精确覆盖原文。
**若这一步不对，后面全都白做**——所以它是独立的、可随时终止的阶段。

### 阶段 1：数据与后端（坐标系已确认可用）

1. 迁移：建 `pdf_annotations` 表 + 两个索引
2. **同步登记 `backup_service.DUMP_TABLES` / `CLEAR_ORDER`**（先做，别等测试报错）
3. service：增删改查 + 按页查询
4. API：6 个端点（注意路由顺序）
5. 测试：`tests/test_p12_pdf_annotations.py`
   - 建/查/改/删
   - 删文档时批注级联清掉
   - 按页过滤正确
   - **备份覆盖面断言**（现有 `test_backup_covers_every_registered_table` 会自动兜住，但要确认它认出新表）

### 阶段 2：前端阅读与批注

1. `PdfViewer.vue`：`pdfjs-dist` 渲染 + 连续滚动 + 页码跳转 + 缩放
2. 文本层划词 → 弹出工具条（高亮 / 加批注 / 出卡片）
3. 高亮层渲染（与文本层同一坐标系叠加）
4. 侧栏批注列表：点条目跳到对应页并闪烁定位
5. 待办：**批注搜索**（在前端已有页面上按 `quote` 匹配）

### 阶段 3：接入三个闭环

1. **导出为笔记**：生成 `《书名》批注.md`，每条含 `> 引文` + 批注 + `[第 N 页]` 链接
2. **闪卡**：选中 → `assist_service` 出题
3. **相关笔记**：导出笔记自动进入 `related_documents` 的候选池（无需代码）

### 阶段 4（可选）：打磨

- 批注颜色与筛选、导出为带原文的 Markdown、PDF 内全文搜索、
  在文档详情页显示「本文档有 N 条批注」

## 八、风险点与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **坐标系换算错**（旋转页 / CropBox / Y 轴方向） | 高亮整体偏移，功能形同虚设 | 阶段 0 独立验证，且**必须用带旋转页的 PDF 测**；用 `Util.transform` 而非手写矩阵 |
| R2 | **PDF.js worker 在 Vite 下加载失败** | 大文件卡死主线程 | `?url` 导入 + 显式设置 `workerSrc`；dev 与 build 都要各测一次（两者行为不同） |
| R3 | **原 PDF 被替换或重排版** | 高亮错位，批注「找不到地方」 | 三重锚定：以 `quote` 重新匹配坐标；匹配失败**显式提示而非静默丢弃** |
| R4 | **漏登记备份表** | 备份/恢复丢批注，且是**静默**的 | 迁移与备份登记**同一次提交**完成；跑 `test_backup_covers_every_registered_table` |
| R5 | **访问口令与 PDF 流式请求冲突** | 局域网模式下 PDF 打不开 | PDF.js 通过 XHR 取文件时带上 `X-Access-Token`；或让 `GET /file` 支持 `?token=` 查询串（中间件已支持该通道） |
| R6 | **大 PDF 内存占用** | 浏览器卡顿/崩溃 | 按需渲染可视页（虚拟滚动）；限制单次渲染页数；后端 `FileResponse` 的 Range 已可用 |
| R7 | **扫描件 PDF 无文本层** | 无法划词 | **明确不支持**，并在 UI 说明（你有 OCR，可以引导用户走「OCR 后按文本笔记读」的路径） |
| R8 | **批注导出笔记与原文重复进检索** | 同一句话被召回两次 | 导出笔记里引文用 `>` 引用块，且**只索引批注文字**——在导出时控制内容，不靠检索层去重 |

## 九、潜在限制（诚实说明）

1. **扫描件 PDF 不可划词**。没有文本层就没有坐标系，只能画框。建议一期不做，UI 上给明确提示。
2. **引文匹配不是 100%**。PDF 文本层抽取可能有断字/连字符差异（如 `re-\nsponse`）。缓解：规范化时去掉软连字符并折叠空白；仍匹配失败则退化为「按页显示、不精确定位」。
3. **不支持手写墨迹**。只做文本高亮 + 注释，不做手写笔迹（那是另一个量级的功能）。
4. **批注不参与向量语义检索**（只参与关键词检索）。因为它走的是「导出成笔记」的路径，而笔记的向量检索是现成的——实际上**能**参与，这里指的是批注本身不单独建向量。
5. **一次只能对一份 PDF 做批注**，没有跨文档的批注视图。

## 十、与其他可选方案的取舍对比

| 方案 | 优势 | 代价 | 结论 |
|---|---|---|---|
| **A. 引文锚定批注（本方案）** | 锚点稳定、能接三个闭环、复用度极高 | 前端要引入 PDF.js、坐标系有实现风险 | ✅ **推荐** |
| B. 坐标锚定（只存矩形） | 实现最简单 | PDF 换版本/重排版后全部错位；无法做引文检索 | ❌ 太脆 |
| C. 只做「整页收藏」 | 极简 | 没有划线就没有价值，等于一个 PDF 阅读器 | ❌ 不解决问题 |
| D. 把 PDF 抽成文本笔记再批注 | 零 PDF 渲染代码 | 失去**版面语义**（图表、公式、表格位置），学术文献尤其致命 | ❌ 只适合纯文字文档 |
| E. 集成 Zotero / 第三方 | 免开发 | 与「本地个人知识库、数据自主」的定位冲突；且批注无法接进你的双链与复习 | ❌ 违背项目定位 |
| F. 先做测试隔离 / 产出物生成 | 工程健康 / 输出端 | 前者零用户价值，后者需求未确认 | 建议排在批注**之后** |

## 十一、一句话总结建议
