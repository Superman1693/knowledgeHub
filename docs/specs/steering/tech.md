## 2. 存储选型（本项目的关键决策）

### 2.1 结论

**采用 PostgreSQL 18 + pgvector 作为统一存储**，由同一个数据库承担三类职责：

1. **关系数据**：文档元数据、知识片段、分类、标签、会话、消息、面试记录、错题、设置。
2. **向量检索**：知识片段嵌入向量存于 `vector(dim)` 列，建 HNSW 索引。
3. **关键词/模糊检索**：基于 `pg_trgm` 的 GIN 索引实现子串与相似度匹配。

### 2.2 选型理由

- 本机已安装 PostgreSQL 18.4 且正在运行（5432 端口监听），`server_encoding = UTF8`。
- 本机 PostgreSQL 已安装 **pgvector 0.8.2** 扩展（另含 pg_trgm 1.6、pgcrypto 1.4、uuid-ossp 1.1），向量能力开箱即用。
- 一个库同时覆盖关系 + 向量 + 关键词，**无需额外维护一套向量数据库**，且是生产级方案。
- 项目为单用户本地场景，PG 的资源占用完全可接受。

### 2.3 中文检索策略（重要约束）

本机 PostgreSQL **未安装中文分词器**（无 zhparser / pg_jieba）。因此：

- **不做**依赖 `tsvector` 的中文全文检索（默认分词对中文无效）。
- 关键词检索统一走 **`pg_trgm`**：`ILIKE` 子串匹配 + `similarity()` 相似度排序。
- 语义检索统一走 **pgvector**：`<=>` 余弦距离排序。
- 最终检索结果由"关键词命中 + 语义相似度"按权重融合（混合检索）。

### 2.4 数据库账号与初始化

- 数据库名：`knowledgehub`
- 专用账号：`kh_app`（**不使用** `postgres` 超管账号）
- 连接串通过 `.env` 注入，**严禁硬编码**进源码或提交进仓库
- 建库 / 建号 / 建扩展的具体 SQL 见 `docs/specs/knowledgehub-core/design.md`

### 2.5 存储方案唯一性

本项目**只使用 PostgreSQL 18 + pgvector 一套存储**，不提供其它回退方案：

- 关系、向量、关键词三类职责全部由同一个库承担，避免多套存储之间的数据一致性问题。
- 本机已安装并运行 PostgreSQL 18.4 + pgvector 0.8.2，无需额外部署或安装独立向量数据库。
- `STORAGE_MODE` 仅接受 `postgres`；配置成其它值时，启动日志与 `/api/health` 会明确报错。

## 4. 网络与地址约定

- 前端开发地址：`http://127.0.0.1:5173`（端口可配置）
- 后端 API 默认**只监听 `127.0.0.1`**，**不得**默认监听 `0.0.0.0`
- 数据库连接：`127.0.0.1:5432`
- 不得自动开放公网 / 局域网访问，启动脚本不得修改防火墙规则
- 说明：本机 PostgreSQL 当前 `listen_addresses = '*'`，属于用户既有配置；应用侧仍须保证自身服务只监听回环地址

## 5. AI 接入约定

### 模式 A：本地模型
- 对接 Ollama 或兼容接口，提供服务地址配置
- 支持模型选择、可用性检测、连接失败清晰提示
- 本地模型可用性**不是**文档管理功能的前置条件

### 模式 B：外部 API
- 用户自行填写服务地址、模型名、API 密钥
- 密钥存于本地受保护配置，**不进代码仓库、不进普通日志**
- 默认不发送整份原始文档，仅发送完成任务所需内容
- **严禁**声称外部 API 模式完全离线
- 界面必须清晰显示当前使用本地模型还是外部服务

## 6. 配置与密钥

- 敏感配置（数据库密码、API 密钥）→ 存 `.env`（受 `.gitignore` 保护）
- 非敏感、用户可调配置（默认回答模式、上传大小限制、数据目录）→ 可存数据库 `app_settings`
- 必须提供 `.env.example` 作为模板

## 7. 编码与质量约束

- 后端按功能划分独立模块，**禁止**把所有逻辑堆在单文件
- 前端必须实现真实前后端交互，**禁止**用固定假数据冒充功能
- 所有持久化数据必须能在关闭软件后保留、重启后恢复
- 测试必须真实执行；**未执行的测试不得声称通过**
