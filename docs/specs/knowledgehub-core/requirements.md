# KnowledgeHub 核心闭环 —— 需求文档（requirements.md）

> **规格类型**：Feature Spec（Requirements-First）
> **规格范围**：核心闭环 = 工程搭建与基础设施 + 文档管理 + 知识检索（RAG） + AI 问答
> **不在本规格范围**：知识加工、模拟面试与错题、项目开发辅助（见文末「后续扩展路线图」）
> **需求书写规范**：EARS（Easy Approach to Requirements Syntax）中文句式

---

## 引言

本文档把《KnowledgeHub 开发总提示词》中的核心闭环部分，形式化为**可测试、可追溯**的需求。每条需求包含：

- **用户故事**：以「作为……，我想要……，以便……」描述价值。
- **验收标准**：用中文 EARS 句式书写，每一条都可直接翻译为测试用例。

EARS 句式约定：

| 类型 | 句式 | 用途 |
|---|---|---|
| 普遍性 | 系统应…… | 恒定成立的行为 |
| 事件驱动 | 当……时，系统应…… | 由事件触发 |
| 状态驱动 | 当处于……状态时，系统应…… | 由状态约束 |
| 非期望行为 | 如果……，则系统应…… | 异常/错误分支 |
| 可选特性 | 当启用了……时，系统应…… | 开关控制 |

---

## 术语表

| 术语 | 含义 |
|---|---|
| 知识片段（Chunk） | 文档正文按语义/长度切分后的最小检索单元 |
| 嵌入（Embedding） | 文本经嵌入模型转换得到的向量 |
| 混合检索 | 关键词检索与语义检索的结果按权重融合 |
| 引用 | AI 回答中指向知识库真实原文的定位信息 |
| 本地模型 | 运行在本机的模型服务（如 Ollama） |
| 外部服务 | 用户自行配置的第三方模型 API |
| 回退方案 | 当本机无合适存储时，改用 SQLite + ChromaDB |

## 需求 1：本地优先与隐私保护

**用户故事：** 作为本机使用者，我想要我的所有资料默认只存在本地，以便我的私人知识不会被上传或泄露。

### 验收标准

1. 系统应将原始文档、解析文本、向量索引、会话历史、笔记、导出文件默认保存于本地磁盘。
2. 系统应在本机完成启动、关闭、搜索与文档管理，且不依赖任何云端服务器。
3. 系统不应集成遥测、埋点或数据分析上报。
4. 当用户未主动使用 AI 功能时，系统不应向任何外部服务发送文档内容。
5. 当用户启用外部 API 模式时，系统应在界面清晰提示"该内容将发送至外部服务"。
6. 如果外部服务请求失败，则系统应返回明确错误，且不应生成虚假的成功结果。

---

## 需求 2：本地工程结构与一键启停

**用户故事：** 作为非技术用户，我想要双击脚本就能启动和关闭软件，以便我无需了解命令行也能日常使用。

### 验收标准

1. 系统应提供 Windows 启动脚本 `start.bat` 与停止脚本 `stop.bat`（并提供跨平台 Python 启动入口）。
2. 当执行启动脚本时，系统应依次：检查 Python/Node 环境 → 检查依赖 → 检查配置 → 检查数据库连接 → 初始化数据库结构 → 启动后端 → 启动前端/页面服务 → 显示实际访问地址。
3. 当启动过程中任一步骤失败时，系统应给出清晰的中文错误提示，并指出失败原因与建议操作。
4. 当执行停止脚本时，系统应只终止本项目启动的服务，且不应误杀其他程序。
5. 系统应提供清晰的目录结构，前后端模块边界明确。
6. 系统不应假设用户安装了 Docker、Redis 或其他未在本机存在的服务。

---

## 需求 3：PostgreSQL 数据库与连接管理

**用户故事：** 作为本机使用者，我想要项目使用本机已安装的 PostgreSQL 存储数据，以便复用现有环境、避免额外安装数据库。

### 验收标准

1. 系统应使用 PostgreSQL 18.4 作为主数据库，默认连接 `127.0.0.1:5432`。
2. 系统应使用独立数据库（默认 `knowledgehub`）与专用账号（默认 `kh_app`），不应使用 `postgres` 超级用户账号执行业务操作。
3. 系统应通过 `.env` 注入数据库连接信息，且不应将连接串或密码硬编码进源码。
4. 系统应通过 SQLAlchemy 2.x 与 Alembic 管理数据库结构，支持创建、升级与检查。
5. 当数据库结构变更时，系统应通过 Alembic 迁移完成，且不应直接手工改表。
6. 当连接数据库失败时，系统应给出明确错误（区分"服务未启动""账号密码错误""库不存在"三类原因）。
7. 系统应在启动脚本中提供"初始化数据库"步骤，自动创建所需数据库、账号与扩展（`vector`、`pg_trgm`、`pgcrypto`、`uuid-ossp`）。

## 需求 4：数据库可用性检测与回退

**用户故事：** 作为换机使用者，我想要在本机没有合适数据库时软件能给出回退方案，以便我在新环境下仍能运行。

### 验收标准

1. 当启动时检测到 PostgreSQL 不可用（未安装或未运行）时，系统应给出明确提示，并说明所需版本与启动方式。
2. 当用户确认启用回退方案时，系统应支持切换到 SQLite + ChromaDB，且核心功能（文档管理、检索、问答）保持可用。
3. 当系统运行在回退方案下时，系统应在界面明确标示当前存储模式，避免用户误判。
4. 系统应在文档中提供从 PostgreSQL 方案迁移到回退方案（及反向迁移）的步骤。
5. 当本机已具备可用的 PostgreSQL 与 pgvector 时，系统应默认使用 PostgreSQL 方案。

---

## 需求 5：文档导入与多格式解析

**用户故事：** 作为本机使用者，我想要导入多种格式的资料并被正确解析，以便我的知识能被统一管理。

### 验收标准

1. 系统应支持至少以下格式：Markdown（`.md`）、纯文本（`.txt`）、PDF（`.pdf`）、Word（`.docx`）、Python（`.py`）、JavaScript/TypeScript（`.js/.ts/.jsx/.tsx`）、HTML/CSS（`.html/.css`）、JSON/YAML（`.json/.yaml/.yml`）。
2. 当导入文件时，系统应验证文件类型与大小，并拒绝超出限制的文件。
3. 当解析文档时，系统应尽可能保留标题、章节、代码块与页码结构。
4. 如果遇到无法解析的格式，则系统应给出明确提示，且不应把未经处理的二进制数据当作正文展示。
5. 系统应采用可扩展的解析器设计，以便后续新增格式。
6. 当导入重复文件时，系统应提示用户可能重复，且不应未经确认覆盖原文件。

---

## 需求 6：文档处理流水线与状态

**用户故事：** 作为本机使用者，我想要看到每份文档的处理进度，以便我知道哪些已可用、哪些失败。

### 验收标准

1. 当文档导入后，系统应按顺序执行：验证 → 保存原文件 → 提取文本 → 保存元数据 → 分块 → 生成向量 → 更新索引 → 标记状态 → 展示结果。
2. 系统应维护文档处理状态，取值至少包含：`pending`（等待）、`processing`（处理中）、`indexed`（索引成功）、`failed`（处理失败）。
3. 当处于处理中状态时，系统应在界面显示真实进度，且不应显示虚假进度。
4. 只有实际完成对应任务后，系统才应更新状态。
5. 如果处理失败，则系统应记录失败原因并在界面提供重试入口。

---

## 需求 7：文档管理操作

**用户故事：** 作为本机使用者，我想要对文档进行完整的增删改查与导出，以便长期维护我的知识库。

### 验收标准

1. 系统应支持拖拽上传、批量上传、文件选择上传。
2. 系统应支持文档内容预览与编辑，并在编辑保存时给出明确提示。
3. 系统应支持文档重命名、分类、标签管理与文档检索。
4. 系统应支持将文档导出为 Markdown 或纯文本，且导出内容应与原始记录一致。
5. 系统应支持定位并打开原始文件。
6. 当删除文档时，系统应同步删除数据库记录、原始文件与对应向量索引，避免已删除内容继续出现在搜索结果中。
7. 当执行删除操作时，系统应要求用户二次确认。
8. 系统应支持索引重建，以应对索引损坏或模型更换。

---

## 需求 8：知识分类管理

**用户故事：** 作为本机使用者，我想要用分类组织知识，以便按主题查找资料。

### 验收标准

1. 系统应支持创建、修改（名称/描述）、删除分类。
2. 系统应支持查看分类下的文档、搜索分类与文档、按更新时间排序。
3. 系统应支持按标签筛选分类内文档。
4. 当删除分类时，系统应默认只移除分类关系，且不应删除分类中的原始文档。
5. 系统应支持分类的自由增删改，且分类仅作为组织方式，不承载访问权限语义。

---

## 需求 9：标签管理

**用户故事：** 作为本机使用者，我想要给文档打标签并自动获得标签建议，以便更灵活地组织和检索知识。

### 验收标准

1. 系统应支持为文档添加多个标签。
2. 系统应支持创建、删除、修改标签名称，并支持按标签筛选文档。
3. 系统应支持统计每个标签关联的文档数量。
4. 当启用标签推荐时，系统应基于实际文档内容或已有分类生成建议，且不应声称自动标签一定正确。
5. 系统应能检测相似标签并给出合并提示。

---

## 需求 10：知识片段切分与向量索引

**用户故事：** 作为本机使用者，我想要文档被合理切分并建立向量索引，以便 AI 能基于我的资料回答。

### 验收标准

1. 系统应将文档正文划分为语义合理的知识片段（chunk），并保留片段与原文的定位关系。
2. 每个知识片段应尽量包含：文档 ID、片段 ID、文档标题、章节标题、原始文件名、页码或段落位置、正文、向量索引标识、创建时间、更新时间。
3. 系统应使用 PostgreSQL + pgvector 存储片段向量（`vector(dim)` 列），并建立 HNSW 索引。
4. 系统应确保向量索引实际写入本地 PostgreSQL，而非仅存在于内存。
5. 当文档被修改时，系统应更新其对应片段与向量索引。
6. 当删除文档时，系统应同步删除其片段与向量，且旧片段不应再出现在检索结果中。
7. 当更换嵌入模型导致向量维度变化时，系统应提示用户可能需要重建向量索引。
8. 引用来源必须依据真实元数据构建；无法确定的页码/章节/位置应留空，且不应伪造。

---

## 需求 11：知识检索（关键词 / 语义 / 混合）

**用户故事：** 作为本机使用者，我想要用关键词或自然语言检索我的知识库，以便快速找到相关资料。

### 验收标准

1. 系统应支持按文档标题搜索、按正文关键词搜索、按标签搜索。
2. 系统应支持语义向量检索（pgvector 余弦距离）。
3. 系统应支持关键词与向量的混合检索，并按权重融合候选结果。
4. 系统应支持按分类筛选、按更新时间筛选、多文档联合检索与候选结果排序。
5. 关键词检索应采用 `pg_trgm` 实现子串与相似度匹配，以适配中文（本机无中文分词器）。
6. 当返回检索结果时，系统应显示文档标题、匹配内容片段与相关性信息。
7. 系统应支持从检索结果定位到来源文档的具体章节或片段。
8. 当检索不到相关内容时，系统应返回空结果并明确说明，而不应伪造结果。

---

## 需求 12：RAG 问答流程

**用户故事：** 作为本机使用者，我想要向 AI 提问并获得基于我知识库的回答，以便高效理解和应用我的知识。

### 验收标准

1. 当用户提交问题时，系统应依次执行：分析问题意图 → 检索知识库 → 选出相关文档与片段 → 检查材料是否足够 → 构建上下文 → 调用模型生成回答 → 关联原始文档 → 保存会话。
2. 当检索到足够材料时，系统应基于检索片段生成回答，且不应绕过检索直接让模型自由作答。
3. 当材料不足以回答时，系统应明确告知用户缺少哪些信息，且不应让模型编造知识库中不存在的记录。
4. 系统应支持多轮追问，并在追问中保持必要的上下文。
5. 当模型服务不可用时，系统应返回明确错误，且不应伪造成功回答。

---

## 需求 13：引用生成与可追溯

**用户故事：** 作为本机使用者，我想要每条知识性回答都能点回原文，以便我验证 AI 说的内容是否属实。

### 验收标准

1. 系统应为每条知识库引用尽可能提供：文档名称、章节或段落、相关原文片段、页码或片段定位、打开原始文档的入口。
2. 系统应保证引用内容可追溯到真实文档，且不应创建虚构的文档名、引用片段或页码。
3. 当用户点击引用时，系统应能打开对应文档，并尽可能定位到相关章节或片段。
4. 当回答包含多条来源时，系统应分别标注每条来源对应的片段。

---

## 需求 14：三类信息来源与事实性约束

**用户故事：** 作为本机使用者，我想要清楚区分回答的来源类型，以便判断信息可信度。

### 验收标准

1. 系统应区分并在回答中标注三类来源：📄【知识库原文】、📑【知识库归纳推理】、🌐【联网补充信息】。
2. 【知识库原文】应直接引用本地知识库中实际存在的原文。
3. 【知识库归纳推理】应基于一份或多份实际检索到的文档进行综合分析。
4. 当用户启用了联网搜索且实际获取到外部资料时，系统才应使用【联网补充信息】，并附上真实来源链接。
5. 当未启用联网功能时，系统不应联网，且不应伪称已经联网查询。
6. 当知识库资料不足以支持确定性结论时，系统应说明缺少哪些信息，并区分"已记录事实"与"推断"。
7. 当存在相互矛盾的文档时，系统应同时展示冲突来源。

---

## 需求 15：AI 服务配置（本地模型 / 外部 API）

**用户故事：** 作为本机使用者，我想要自由配置本地模型或外部 API，以便在隐私与效果之间权衡。

### 验收标准

1. 系统应支持模式 A：配置本地模型服务地址、选择可用模型、检测服务是否正常、连接失败时给出清晰提示。
2. 系统应支持模式 B：用户自行填写外部服务地址、模型名称与 API 密钥。
3. 系统应支持分别启用或关闭本地模型与外部服务。
4. 系统应将 API 密钥保存在本地受保护配置中，且不应写入代码仓库或普通日志。
5. 系统应支持配置聊天模型与嵌入模型，并在更换嵌入模型时提示可能需重建索引。
6. 界面应清晰显示当前使用的是本地模型还是外部服务。
7. 系统应支持配置请求超时。
8. 本地模型可用性不应成为文档管理等非 AI 功能的前置条件。

---

## 需求 16：聊天界面与会话历史

**用户故事：** 作为本机使用者，我想要管理会话并查看历史，以便持续追问和回溯对话。

### 验收标准

1. 系统应支持创建新会话、查看历史会话、删除会话、修改会话标题。
2. 系统应支持连续追问、Markdown 渲染、代码语法高亮、复制回答。
3. 系统应支持展示来源引用与查看关联文档。
4. 系统应支持重新生成回答与请求中止。
5. 系统应提供加载状态与错误提示。
6. 会话历史应保存在本地 PostgreSQL 中，且关闭软件后仍能恢复。

---

## 需求 17：三种输出模式与专属术语词典

**用户故事：** 作为本机使用者，我想要按不同详略程度获得回答，并能查询我的专属术语，以便适应不同场景。

### 验收标准

1. 系统应支持三种回答模式：**详细解释**（原理/背景/示例/注意事项）、**极简要点**（核心结论/关键词/记忆点）、**通俗举例**（通俗语言与具体示例）。
2. 系统应支持在当前会话中切换输出模式。
3. 系统应优先检索本地术语词典与相关项目文档，用于解释技术缩写、项目自定义名词、框架术语、个人习惯用语与项目组件名称。
4. 当术语词典中没有相关信息时，系统应明确说明无法从现有资料确认其含义，且不应臆造。

---

## 需求 18：系统配置页与首次启动

**用户故事：** 作为本机使用者，我想要一个统一的设置页面和顺畅的首次启动，以便完成初始化并调整偏好。

### 验收标准

1. 系统应提供统一设置页面，包含：AI 服务类型、模型服务地址、聊天模型名称、嵌入模型配置、API 密钥、请求超时、默认回答模式、默认数据目录、文档上传大小限制、本地模型服务检查、向量索引状态、数据备份与恢复。
2. 系统应区分哪些配置写入数据库、哪些保存在本地受保护环境文件。
3. 当首次运行时，系统应：创建所需数据目录 → 创建/迁移数据库结构 → 初始化本地索引 → 检查必要配置 → 检查 AI 服务是否可用 → 显示下一步操作说明。
4. 当 AI 模型尚未配置时，系统仍应能启动、管理本地文档并使用不依赖 AI 的功能。
5. 当数据目录被用户修改时，系统应写入用户指定目录，且不应产生多份分散的数据副本。

## 需求 19：数据备份与恢复

**用户故事：** 作为本机使用者，我想要备份和恢复我的知识库，以便防止数据丢失或迁移设备。

### 验收标准

1. 系统应提供：本地数据目录查看、手动备份、手动恢复、数据库备份、文档及附件备份、向量索引重建、文档彻底删除、临时文件与缓存清理。
2. 当执行备份时，系统应说明备份包含哪些数据。
3. 当执行恢复时，系统应先检查备份的完整性与版本兼容性，必要时要求用户确认。
4. 当执行整个知识库清空、覆盖恢复或批量删除时，系统应设置明确的二次确认。
5. 当清理缓存时，系统不应误删原始文档、正式笔记或其他重要资料。

## 需求 20：测试与质量要求

**用户故事：** 作为本机使用者，我想要交付的软件经过真实验证，以便我能信任它的功能确实可用。

### 验收标准

1. 系统应提供可实际执行的测试命令与真实执行结果，且未执行的测试不应被声称通过。
2. 系统应通过基础测试：应用能启动、数据库能初始化、文档可上传/读取/删除、笔记可保存/修改、关闭后数据仍在、重启后可恢复、搜索可返回相关文档、处理失败有明确提示。
3. 系统应通过 RAG 测试：文档可被正确解析与分块、向量索引实际写入本地存储、关键词检索可用、语义检索可用、文档修改后索引更新、删除文档后旧片段不再出现、回答引用对应真实来源、无相关资料时不编造、模型不可用时不伪造成功。
4. 系统应通过 AI 功能测试：本地模型配置可读取、外部 API 配置可加载、请求失败时错误处理正常、聊天历史可恢复、导出内容与原始记录一致。
5. 系统应通过数据安全测试：密钥不硬编码、不向未配置的外部服务自动传输文档、不记录不必要的敏感正文、删除文档后清理索引、备份与数据库不进入源码仓库、本地服务默认不监听公网或局域网接口。

## 后续扩展路线图（本规格不展开实现）

以下模块沿用同一套 Steering 约束与存储架构，作为后续独立 Feature Spec 实现。建议优先级与依赖如下：

| 优先级 | 模块 | 主要能力 | 依赖 |
|---|---|---|---|
| P1 | AI 知识加工 | 笔记整理与归档、标签推荐、冗余检测、跨文档知识关联、思维导图 | 需求 5–10（文档、分块、索引） |
| P2 | 学习辅助 | 模拟面试（多方向/多难度）、评分与点评、错题管理、快捷复习 | 需求 12–14（问答、引用） |
| P2 | 项目开发辅助 | 代码评审、故障排查、需求拆解、项目时间线 | 需求 11–14（检索、问答） |

**扩展模块的共性约束（沿用核心闭环）：**

- 事实/观点/计划/推断必须分离，不得把计划写成已完成、把推断写成用户观点。
- 复习与面试不得虚构用户曾经答错的题目。
- 代码评审必须区分"知识库记录"与"AI 新提出的建议"。
- 故障排查未经验证时不得把可能原因说成确定根因。
- 时间线无法从原文确认日期时应标注为未知，不得推测。
