## 二、缺陷清单

### 🔴 P0-1　备份/恢复缺失两张表，且父子块顺序会导致恢复失败

**位置**
- `backend/app/services/backup_service.py:30-50`（`CLEAR_ORDER` / `DUMP_TABLES`）
- `backend/app/services/backup_service.py:137-196`（`restore_backup`）

**表现**
1. 备份 zip 中**不含** `glossary_terms`（术语词典）与 `quiz_records`（错题本）。
2. 恢复时按 `select(Chunk)` 的返回顺序插入片段，但该查询**没有 ORDER BY**。

**影响范围**
- 用户辛苦维护的**术语词典**与**错题记录**在任何备份/恢复中都会丢失；
- 恢复到新机器时，若插入顺序中出现「子块早于父块」，`chunks.parent_id` 外键立即违约，
  **整个恢复事务失败**，用户拿到的是一个 500 错误 + 半损坏状态。

**成因（已用数据证明）**
- `DUMP_TABLES`/`CLEAR_ORDER` 是硬编码清单，新增 `quiz_records`、`glossary_terms` 时未同步；
- `Chunk` 模型只有 `parent_id` **列**，没有配置自引用 `relationship()`，
  因此 SQLAlchemy 的 unit-of-work **无法推断父子插入顺序**，只能按添加顺序插入；
- 实测本库 146 个片段中有 **14 个「子块物理位置早于父块」**（用 `ctid` 比较），
  即当前数据**必然**触发该问题。

**修复方案**
```python
# 1) 补齐表清单（先父后子，quiz/glossary 放最后）
CLEAR_ORDER = [
    "quiz_records", "glossary_terms",          # 先删（引用 documents/chunks）
    "messages", "conversations", "document_tags",
    "chunks", "documents", "tags", "categories", "app_settings",
]
DUMP_TABLES = [
    ("categories", Category), ("tags", Tag),
    ("documents", Document), ("conversations", Conversation),
    ("glossary_terms", GlossaryTerm), ("quiz_records", QuizRecord),
    ("chunks", Chunk), ("messages", Message), ("app_settings", AppSetting),
]

# 2) chunks 显式排序：父块（parent_id IS NULL）在前，子块在后
rows = db.execute(
    select(Chunk).order_by(Chunk.parent_id.is_not(None), Chunk.chunk_index)
).scalars().all()
```
> 更稳妥：恢复片段时先插入 `parent_id IS NULL` 的行，`flush()` 后再插入有 `parent_id` 的行。
> 建议同时在 `Chunk` 上加 `relationship("Chunk", remote_side="Chunk.id")`，让 ORM 自动排序。

**验证方式**：备份 → 删库重建 → 恢复 → 核对 `glossary_terms`/`quiz_records` 行数、`chunks` 行数、
以及 `SELECT count(*) FROM chunks c JOIN chunks p ON c.parent_id=p.id`（父子关联数）。

### 🔴 P0-2　恢复备份存在 Zip Slip（路径穿越写盘）

**位置**：`backend/app/services/backup_service.py:188-194`

```python
for member in zf.namelist():
    if member.startswith("files/"):
        rel = member[len("files/"):]          # 未校验 ".."
        target = settings.data_path / rel     # 可逃出数据目录
        target.write_bytes(zf.read(member))
```

**表现**：构造一个含 `files/../../../evil.bat` 条目的 zip 并触发恢复，文件会写到数据目录之外。

**影响范围**：本地单用户应用，风险等级中；但一旦用户从外部获取备份文件即可能被利用，
且会**覆盖任意可写路径**。

**修复方案**
```python
target = (settings.data_path / rel).resolve()
base = settings.data_path.resolve()
if not target.is_relative_to(base):          # Python 3.9+
    logger.warning("跳过非法备份条目：%s", member)
    continue
```

### 🟠 P1-1　重复标签名直接触发 HTTP 500

**位置**：`backend/app/services/tag_service.py:123-141`（`set_document_tags`）

**表现（实测）**
```
POST /api/tags/document/<doc_id>  {"names":["测试标签X","测试标签X","测试标签X"]}
→ HTTP 500
{"code":"INTERNAL_ERROR","message":"服务器内部错误",
 "detail":"UniqueViolation: 重复键违反唯一约束 document_tags_pkey ..."}
```

**影响范围**：前端标签选择器若允许重复输入（或用户从「AI 推荐」结果里重复点选），
保存标签即报 500；`document_tags` 主键为 `(document_id, tag_id)`。

**成因**：循环内对每个 `name` 都 `tags.append(tag)`，未按 `tag.id` 去重。

**修复方案**
```python
seen: set[uuid.UUID] = set()
tags: list[Tag] = []
for raw in names:
    name = raw.strip()
    if not name:
        continue
    tag = db.execute(select(Tag).where(Tag.name == name)).scalars().first()
    if not tag:
        tag = Tag(name=name); db.add(tag); db.flush()
    if tag.id in seen:            # 关键：去重
        continue
    seen.add(tag.id)
    tags.append(tag)
doc.tags = tags
```

### 🟠 P1-2　扩展模块把 404 / 422 一律吞成 503

**位置**
- `backend/app/api/insights.py:50-51, 61-62`
- `backend/app/api/devhelper.py:28-29, 43-44, 56-57, 72-73`，以及 `:83`（显式抛错类型错误）
- `backend/app/api/learning.py:31-32, 53-54`

```python
try:
    return await insight_service.build_mindmap(db, document_id)
except AIUnavailableError:
    raise
except Exception as exc:                       # ← 把 NotFoundError / ValidationError 也吞了
    raise AIUnavailableError(f"生成思维导图失败：{exc}") from exc
```

**表现（实测）**

| 请求 | 期望 | 实际 |
|---|---|---|
| `POST /api/insights/mindmap/<不存在的uuid>` | 404 | **503** |
| `POST /api/devhelper/review {"code":""}` | 422 | **503** |
| `GET /api/devhelper/timeline/dates/<不存在的uuid>` | 404 | **503**（且 `message="文档不存在"`） |

**影响范围**：前端无法区分「参数错了」和「AI 服务挂了」，一律弹「AI 不可用」提示；
监控/日志也难以定位。`AppError` 子类（`NotFoundError`/`ValidationError`）都继承自 `Exception`，
所以会被这个兜底分支捕获。

**反例**：`POST /api/tags/document/<不存在的uuid>` 正确返回 404（该路由没有包 try），
说明这是**局部实现不一致**而非设计如此。

**修复方案**：兜底分支只包住真正的未知异常，`AppError` 一律放行：
```python
from app.core.exceptions import AppError
...
except AppError:
    raise                      # 404/422/503 等业务异常原样透出
except Exception as exc:
    raise AIUnavailableError(f"生成思维导图失败：{exc}") from exc
```
并把 `devhelper.py:83` 的 `raise AIUnavailableError("文档不存在")` 改为 `raise NotFoundError("文档不存在")`。

.order_by(func.coalesce(

### 🟡 P2-2　前端校验错误显示为 `[object Object]`

**位置**：`frontend/src/api/client.ts:12-16`

```ts
const message = error?.response?.data?.message || error?.response?.data?.detail || ...
ElMessage.error(String(message))
```

**表现（实测）**：FastAPI 的参数校验失败返回的是**数组**：
```json
{"detail":[{"type":"greater_than_equal","loc":["query","page"],
            "msg":"Input should be greater than or equal to 1",...}]}
```
`String([{...}])` → `"[object Object]"`，用户看不到任何有效信息。

**影响范围**：所有 `page=0`、`page_size=200`、非法 uuid 等参数错误场景，提示均为 `[object Object]`。

**修复方案**
```ts
function pickMessage(err: any): string {
  const d = err?.response?.data
  if (typeof d?.message === 'string') return d.message
  if (typeof d?.detail === 'string') return d.detail
  if (Array.isArray(d?.detail)) {                    // FastAPI 校验错误
    return d.detail.map((x: any) => `${x.loc?.slice(1).join('.')}: ${x.msg}`).join('；')
  }
  return err?.message || '请求失败'
}
```

### 🟡 P2-3　文档详情路由复用导致数据不刷新

**位置**：`frontend/src/layouts/MainLayout.vue:72`（`<router-view />` 无 `:key`）
+ `frontend/src/views/DocumentDetailView.vue:111`（`const id = route.params.id` 只在 setup 读一次）

**表现**：在 `/documents/A` 页面直接跳到 `/documents/B`（同一路由记录、仅 params 变化）时，

同时 `watch(() => route.query.chunk)` 会触发 `locateChunk()`，但用的是 A 的片段列表，定位静默失败。

**影响范围**：所有「文档详情 → 文档详情」的直接跳转；当前主要入口来自问答/检索页，
从其它路由进入时会重新挂载，因此影响有限，但属于确定性缺陷。

**修复方案**（任选，推荐 1）
```vue
<!-- 1) 最省事：让不同 fullPath 强制重建 -->
<router-view :key="route.fullPath" />
```
```ts
// 2) 或在本组件监听 id 变化
watch(() => route.params.id, async () => { await load(); await locateChunk() })
```

## 五、结论与建议的修复顺序

1. **P0-1 / P0-2**：备份恢复是「数据最后一道防线」，缺表 + 顺序 + 穿越三项必须一起修，并补往返测试。
2. **P1-1**：重复标签 500 是**用户可直接触发的崩溃**，改动极小，优先修。
3. **P1-2**：扩展模块状态码统一，顺手把 `AppError` 放行逻辑抽成装饰器或中间件，避免逐处重复。
4. **P2**：会话排序与前端错误展示影响日常体验，建议同批修复。
5. **P3**：可并入同一次迭代，不必单独排期。

> 规格中「错题本只查真实答错题」「时间线不推测日期」「冗余检测只提示不改内容」等
> **6 条事实性硬约束经核查均未被破坏**，可在修复其它问题时作为回归底线保持不变。
